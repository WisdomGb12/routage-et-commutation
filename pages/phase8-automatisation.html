Phase 8

Automatisation et Programmabilité

Le pont entre Dev et Ops

Découvrez comment appliquer des concepts de développement logiciel (APIs, JSON, automatisation) pour gérer des infrastructures réseau à grande échelle avec le SDN, Ansible et Cisco DNA Center.

1. Réseau traditionnel vs Réseau programmable

Historiquement, l'administration réseau consistait à se connecter via SSH ou console (CLI) à chaque équipement pour taper des commandes de configuration.

Gestion Traditionnelle

  • Configuration équipement par équipement.
  • Sujet aux erreurs humaines (fautes de frappe).
  • Très difficile de maintenir une cohérence (Configuration Drift).
  • Prend beaucoup de temps pour déployer de nouveaux services.

Automatisation (Programmabilité)

  • Gestion de l'infrastructure comme du code (Infrastructure as Code).
  • Déploiement massif et reproductible via des scripts ou outils (Ansible, Python).
  • Cohérence garantie et temps de déploiement drastiquement réduit.

2. SDN (Software-Defined Networking)

Dans un routeur ou switch classique, deux rôles (plans) cohabitent dans la même boîte matérielle :

  • Control Plane (Plan de contrôle) : L'intelligence (les protocoles de routage comme OSPF, la table ARP, STP). C'est lui qui "apprend" le réseau.
  • Data Plane (Plan de données) : Le "muscle". Il prend les paquets entrants et les expédie le plus vite possible vers le port de sortie en se basant sur les décisions du Control Plane.

L'approche SDN

Le SDN sépare physiquement ces deux plans :

  • Le Control Plane est retiré des équipements et centralisé dans un serveur appelé Contrôleur SDN.
  • Les équipements réseau ne gardent que le Data Plane. Ce sont de simples commutateurs très rapides qui attendent les ordres du Contrôleur.

Les APIs dans le SDN

  • Southbound API : Interface entre le Contrôleur et les équipements physiques (ex: OpenFlow, NETCONF). Utilisée pour envoyer les règles de routage aux switches.
  • Northbound API : Interface entre le Contrôleur et les applications (vos scripts Python, l'interface graphique). Ce sont généralement des API REST.

3. API REST et format JSON

Une API (Application Programming Interface) permet à un programme de discuter avec un autre. L'API REST (Representational State Transfer) utilise le protocole web HTTP classique; les échanges sont souvent formatés en JSON.

Les méthodes HTTP (CRUD)

  • GET : Lire (Récupérer l'état d'une interface).
  • POST : Créer (Ajouter un nouveau VLAN).
  • PUT / PATCH : Mettre à jour (Modifier la description d'une interface).
  • DELETE : Supprimer (Supprimer une route).

Authentification simple (token) — exemple

Beaucoup d'APIs réseau utilisent un mécanisme d'authentification par token. Exemple simplifié :

Obtenir un token (curl)
curl -s -X POST https://api.example.local/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"Secret123"}'

# Réponse:
# {"token":"eyJhbGciOiJI..."}
Exemple : requête GET avec token
curl -s -X GET https://api.example.local/devices/1/interfaces \
  -H "Authorization: Bearer eyJhbGciOiJI..." \
  -H "Accept: application/json"

# Réponse (JSON):
# {"interfaces": [{"name":"GigabitEthernet0/1","status":"up"}, ...]}

Exemple POST (créer un VLAN)

POST VLAN
curl -X POST https://api.example.local/vlans \
  -H "Authorization: Bearer " \
  -H "Content-Type: application/json" \
  -d '{"vlan_id": 30, "name": "Dev"}'

# Réponse: 201 Created
# {"id":30, "name":"Dev", "status":"created"}

Codes HTTP utiles

  • 200 : OK (GET)
  • 201 : Créé (POST)
  • 204 : Pas de contenu (DELETE réussi)
  • 400 : Requête invalide
  • 401 : Non authentifié
  • 403 : Interdit
  • 500 : Erreur serveur

Le format JSON (JavaScript Object Notation)

Exemple de réponse structurée — identique à la CLI mais plus facilement traitable par un programme :

Exemple de réponse API (JSON) pour une interface réseau 
{
  "interface": {
    "name": "GigabitEthernet0/1",
    "description": "Lien vers Serveur Web",
    "status": "up",
    "ip_address": "192.168.10.1",
    "mask": "255.255.255.0",
    "active": true
  }
}

Ces exemples permettent de comprendre les échanges et d'écrire de petits scripts (curl, Python requests) pour automatiser des vérifications ou des modifications.

4. Introduction à Ansible

Ansible est un outil d'automatisation open source très populaire en réseau. Il est "agentless" (aucun agent à installer sur les switches, il utilise SSH ou NETCONF selon le module).

Vocabulaire clé

  • Inventory : Le fichier listant tous vos équipements réseau et leurs IP.
  • Playbook : Un fichier écrit en YAML contenant les instructions (recette) à appliquer.
  • Task : Une étape individuelle dans un Playbook (ex: "Créer VLAN 10").
  • Module : Le code sous-jacent exécuté par la Task (Ansible a des modules spécifiques pour Cisco IOS, comme cisco.ios.ios_config ou cisco.ios.ios_vlans).

L'Idempotence

C'est le concept central d'outils comme Ansible. L'idempotence signifie que l'exécution répétée d'un script donnera toujours le même résultat final sans tout casser. Exécuter deux fois un playbook correctement écrit doit afficher changed: 0 à la seconde exécution.

Exemple d'inventory (fichier inventory.ini)

[switches]
sw1 ansible_host=10.0.0.11 ansible_user=admin ansible_password=AdminPass ansible_network_os=cisco.ios ansible_connection=network_cli

Exemple de playbook (playbook.yml)

---
- name: Provisionner des switches Cisco
  hosts: switches
  gather_facts: no

  tasks:
    - name: Créer le VLAN 30
      cisco.ios.ios_vlans:
        config:
          - vlan_id: 30
            name: Dev
        state: merged

    - name: Configurer la description d'interface
      cisco.ios.ios_config:
        lines:
          - description Lien_vers_Serveur_Dev
        parents: interface GigabitEthernet1/0/1

Exécution (exemples) :

ansible-playbook -i inventory.ini playbook.yml
# Si vous utilisez des credentials stockés, vous pouvez automatiser la connexion (vault, ansible.cfg)

Bonnes pratiques

  • Utiliser des variables pour les credentials et les séparer du code (ansible-vault).
  • Tester d'abord sur un lab, puis passer en production avec review et validation.
  • Rendre les playbooks idempotents et limiter les changements non désirés.

Labs recommandés

Lab A — REST API : interrogation et création

Objectif : Utiliser curl pour récupérer des informations (GET) et créer un VLAN (POST) sur une API mock ou RESTCONF si disponible.

  1. Utiliser un service de test (ex: httpbin.org) ou votre API locale pour tester un GET.
  2. Simuler l'obtention d'un token puis faire une requête GET protégée.
  3. Rédiger un petit script bash utilisant curl et jq pour extraire et afficher le nom des interfaces.

Vérifications : Le script affiche les interfaces et le POST retourne 201/200 selon l'API.

Lab B — Ansible : Provisionner un VLAN

Objectif : Exécuter le playbook ci-dessus sur un switch simulé / lab et vérifier l'idempotence.

  1. Préparer inventory.ini et playbook.yml (voir exemples).
  2. Exécuter : ansible-playbook -i inventory.ini playbook.yml et observer les tâches marquées changed.
  3. Relancer la même commande — les tâches déjà appliquées doivent afficher changed: 0.

Vérifications : Le VLAN existe sur le switch; seconde exécution ne change rien.

5. Cisco DNA Center & Intent-Based Networking (IBN)

Cisco DNA Center est la plateforme de gestion centralisée et le contrôleur SDN de Cisco pour les réseaux d'entreprise.

Intent-Based Networking (IBN)

Dans un réseau traditionnel, l'ingénieur traduit le besoin "La RH doit accéder au serveur de paie" en commandes techniques : il crée un VLAN, attribue des IP, écrit des ACLs complexes ligne par ligne.

L'IBN (Réseau basé sur l'intention), via le DNA Center, change cela. L'administrateur définit son "intention" dans une interface graphique (ex: "Règle : Groupe RH -> a le droit d'accès -> Groupe Serveurs"). Le contrôleur s'occupe de traduire automatiquement cette intention en commandes techniques (CLI ou API) et de les déployer sur les équipements appropriés, tout en vérifiant en permanence que l'intention est bien respectée.

Rôles du DNA Center

  • Design : Cartographie, sites, serveurs DNS/DHCP globaux.
  • Policy : Création des intentions (règles de sécurité, QoS).
  • Provision : Déploiement automatique des configurations (Zero-Touch Provisioning - ZTP).
  • Assurance : Surveillance IA avancée, dépannage proactif et vérification de santé.
