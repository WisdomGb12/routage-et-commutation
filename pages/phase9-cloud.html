Phase 9

Réseaux et Cloud Networking

Durée estimée : 2-3 semaines

Cette phase introduit les concepts réseau dans le cloud public (AWS, Azure, GCP). Les notions sont conceptuelles et comparées aux équivalents Cisco que vous maîtrisez déjà.

Sommaire

1. Modèles de cloud et responsabilités réseau

Le cloud se décline en trois modèles de service. La responsabilité réseau varie selon le modèle :

Modèle Responsabilité réseau client Exemple
IaaS (Infrastructure) VPC, subnets, ACLs, routes, SG AWS EC2, Azure VM
PaaS (Plateforme) Connectivité d'accès uniquement AWS RDS, Azure App Service
SaaS (Logiciel) Presque aucune (accès Internet) Microsoft 365, Salesforce
Modèle de responsabilité partagée

Le provider gère l'infrastructure physique. Vous restez responsable des règles de sécurité réseau, des VPCs, des routes et des configurations dans votre tenant. Une mauvaise configuration de Security Group peut exposer vos ressources publiquement.

2. VPC / VNet : réseau virtuel privé

Un VPC (Virtual Private Cloud) ou VNet (Azure) est l'équivalent cloud d'un réseau privé isolé. C'est le premier objet à créer avant toute ressource cloud.

Analogie avec les réseaux traditionnels

  • VPC = switch L3 + routeur = réseau d'entreprise isolé
  • Subnet public = VLAN avec accès Internet (Internet Gateway)
  • Subnet privé = VLAN interne sans accès direct à Internet
  • Internet Gateway = routeur de bordure vers Internet
  • NAT Gateway = NAT/PAT pour les instances privées
  • Route Table = table de routage associée à chaque subnet

Structure typique d'un VPC multi-tiers

VPC : 10.0.0.0/16 | ├── Subnet Public : 10.0.1.0/24 → Internet Gateway | └── Instances frontend (web), Load Balancer | ├── Subnet Privé : 10.0.2.0/24 → NAT Gateway (sortie) | └── Instances backend (API) | └── Subnet DB : 10.0.3.0/24 → Aucune route sortante └── Bases de données (RDS, PostgreSQL)

Tables de routage associées

# Route Table - Subnet Public Destination Target 0.0.0.0/0 igw-xxxxx (Internet Gateway) 10.0.0.0/16 local # Route Table - Subnet Privé Destination Target 0.0.0.0/0 nat-xxxxx (NAT Gateway, dans subnet public) 10.0.0.0/16 local # Route Table - Subnet DB Destination Target 10.0.0.0/16 local (Aucune route vers Internet)
Bonne pratique : principe du moindre privilège

Ne donnez accès Internet qu'aux subnets qui en ont absolument besoin. Les bases de données et backends doivent être dans des subnets privés sans route directe vers Internet — exactement comme avec des VLANs isolés en réseau traditionnel.

3. Routage cloud, peering et transit

VPC Peering

Le VPC Peering relie deux VPCs via un lien privé interne (pas d'Internet). Comparable à une liaison point-à-point entre deux routeurs d'entreprise.

  • Les plages CIDR des deux VPCs ne doivent pas se chevaucher
  • Le routage n'est pas transitif : si A est peered avec B, et B avec C, A ne voit pas C automatiquement
  • Il faut ajouter des routes manuellement dans chaque route table
# Après création du peering VPC-A <-> VPC-B # Ajouter dans Route Table de VPC-A : Destination Target 10.1.0.0/16 pcx-xxxxx (Peering Connection) # Ajouter dans Route Table de VPC-B : Destination Target 10.0.0.0/16 pcx-xxxxx (Peering Connection)

Transit Gateway (Hub-and-Spoke)

Pour interconnecter de nombreux VPCs, le Transit Gateway (AWS) ou Virtual WAN Hub (Azure) centralise le routage — comme un routeur de cœur dans un réseau hiérarchique.

On-Prem ──── VPN ────┐ VPC-A ───────────────┤ VPC-B ───────────────┤── Transit Gateway ─── Route Tables centralisées VPC-C ───────────────┤ VPC-Prod ────────────┘
Attention aux chevauchements CIDR

Planifiez votre plan d'adressage IP avant de créer vos VPCs. Deux VPCs avec des CIDRs qui se chevauchent (ex: 10.0.0.0/16 et 10.0.0.0/24) ne peuvent pas être mis en peering — exactement comme deux VLANs avec des plages IP identiques.

4. Sécurité : Security Groups et Network ACL

Security Groups (SG)

Un Security Group est un pare-feu stateful attaché à une interface réseau (instance). Comparaison :

  • Stateful : si vous autorisez le trafic entrant, la réponse sort automatiquement
  • Seules les règles Allow existent — pas de règle Deny explicite
  • Peut référencer d'autres Security Groups (ex: backend accepte uniquement du SG frontend)
# Security Group "SG-Frontend" (port 80/443 depuis Internet) Type Protocol Port Range Source Inbound TCP 80 0.0.0.0/0 Inbound TCP 443 0.0.0.0/0 Outbound All All 0.0.0.0/0 # Security Group "SG-Backend" (port 8080 depuis SG-Frontend uniquement) Type Protocol Port Range Source Inbound TCP 8080 sg-frontend-id Outbound All All 0.0.0.0/0 # Security Group "SG-DB" (port 5432 depuis SG-Backend uniquement) Type Protocol Port Range Source Inbound TCP 5432 sg-backend-id

Network ACL (NACL)

Les NACL s'appliquent au niveau du subnet, sont stateless (comme les ACL Cisco étendues), et évaluent les règles par ordre numérique croissant.

# NACL Subnet Privé — comparaison avec ACL Cisco Rule Type Protocol Port Source Allow/Deny 100 Inbound TCP 8080 10.0.1.0/24 ALLOW ← depuis subnet public 200 Inbound TCP 443 0.0.0.0/0 DENY * Inbound All All 0.0.0.0/0 DENY ← règle implicite ! Équivalent Cisco access-list 110 permit tcp 10.0.1.0 0.0.0.255 any eq 8080 access-list 110 deny tcp any any eq 443 access-list 110 deny ip any any

5. Connectivité hybride : VPN et Direct Connect

Site-to-Site VPN Cloud

Permet de relier un datacenter on-premises à un VPC via un tunnel IPSec chiffré. Le principe est identique au VPN site-to-site Cisco vu en Phase 5.

On-Premises Router ←── IPSec Tunnel ──→ Virtual Private Gateway (VGW) (Cisco IOS/Fortinet) | VPC (10.0.0.0/16) ! Côté Cisco (on-prem) crypto isakmp policy 10 encr aes hash sha256 authentication pre-share group 14 crypto isakmp key CLOUDKEY address <VGW-Public-IP> crypto ipsec transform-set MYSET esp-aes 256 esp-sha256-hmac mode tunnel crypto map CLOUDMAP 10 ipsec-isakmp set peer <VGW-Public-IP> set transform-set MYSET match address CLOUD-TRAFFIC

Direct Connect / ExpressRoute

Pour des raisons de latence, bande passante ou conformité, une connexion privée dédiée peut remplacer le VPN :

  • AWS Direct Connect : lien dédié 1-100 Gbps via un partenaire
  • Azure ExpressRoute : même principe avec BGP
  • Le BGP propage les routes entre on-prem et VPC
  • Pas de transit Internet — latence prévisible et SLA garanti
! BGP côté on-prem pour Direct Connect router bgp 65001 neighbor <DX-BGP-IP> remote-as 7224 ← AS Amazon network 192.168.0.0 mask 255.255.0.0 neighbor <DX-BGP-IP> route-map CLOUD-EXPORT out

6. Load Balancing dans le cloud

Les cloud providers proposent des load balancers managés, disponibles en deux couches :

  • L4 (NLB / Azure LB) : TCP/UDP, ultra-rapide, IP statique possible, pas d'inspection HTTP
  • L7 (ALB / Application Gateway) : HTTP/HTTPS, routage par chemin URL, terminaison SSL, WAF intégré
Internet | [ALB - Application Load Balancer] ← SSL termination, règles HTTP | ├── /api/* → Target Group API (instances backend) └── /* → Target Group Web (instances frontend)
Health Checks automatiques

Contrairement à HSRP/VRRP qui surveille les interfaces, les LB cloud vérifient activement la santé des instances (HTTP 200, TCP connect). Si une instance tombe, elle est retirée automatiquement du pool — sans intervention manuelle.

7. SD-WAN et évolution vers le cloud

Le SD-WAN (Software-Defined WAN) modernise la connectivité WAN en découplant le plan de contrôle du plan de données — exactement comme SDN pour les LAN.

Avantages clés

  • Agrégation de liens hétérogènes (MPLS + Internet + 4G/5G)
  • Routage applicatif dynamique (QoS par application)
  • Chiffrement de bout en bout automatique
  • Intégration native avec les cloud providers (AWS, Azure)

Comparaison WAN traditionnel vs SD-WAN

WAN Traditionnel : Site A ──── MPLS ──── HQ Router ──── Internet ──── Cloud (backhaul obligatoire, latence élevée) SD-WAN : Site A ──── SD-WAN Edge ──── Internet direct ──── Cloud ──── MPLS (backup) (routage direct, latence optimisée)
SD-WAN ≠ remplacement complet MPLS

Pour les applications critiques nécessitant un SLA garanti (voix, ERP temps réel), le MPLS reste souvent nécessaire en combinaison avec le SD-WAN. Le SD-WAN est un outil de routage intelligent, pas une solution de remplacement systématique.

8. Labs et cas pratiques

Lab A — Concevoir un VPC multi-tiers

Objectif : Concevoir sur papier (ou dans AWS Free Tier) un VPC pour une application 3-tiers.

  1. Définir le CIDR du VPC : 10.0.0.0/16
  2. Créer 3 subnets dans 2 AZ (6 subnets total pour la HA)
  3. Attacher une Internet Gateway au VPC
  4. Créer un NAT Gateway dans le subnet public
  5. Configurer les route tables : public → IGW, privé → NAT
  6. Créer 3 Security Groups (frontend, backend, db) avec les règles minimales
# Vérification AWS CLI aws ec2 describe-vpcs --query 'Vpcs[*].[VpcId,CidrBlock,State]' aws ec2 describe-subnets --query 'Subnets[*].[SubnetId,CidrBlock,AvailabilityZone]' aws ec2 describe-route-tables --query 'RouteTables[*].Routes' aws ec2 describe-security-groups --query 'SecurityGroups[*].[GroupName,IpPermissions]'

Lab B — VPC Peering entre deux environnements

Objectif : Relier un VPC Dev (10.1.0.0/16) et un VPC Prod (10.0.0.0/16) sans chevauchement.

  1. Créer la Peering Connection depuis VPC Dev vers VPC Prod
  2. Accepter la demande côté Prod
  3. Ajouter la route 10.1.0.0/16 → pcx-xxx dans la route table Prod
  4. Ajouter la route 10.0.0.0/16 → pcx-xxx dans la route table Dev
  5. Mettre à jour les Security Groups pour autoriser le trafic entre VPCs
# Test de connectivité ping 10.0.1.10 ← depuis instance dans VPC Dev vers VPC Prod # Vérifier que la route est présente dans les RT aws ec2 describe-route-tables --filters Name=vpc-id,Values=vpc-dev
